# M1 — Identity, Households & Secure Setup

**Status:** ready for implementation
**Depends on:** M0 (walking skeleton)
**Goal:** A first-time self-hoster can open Expenser, create the owner account and
household through a polished wizard, sign out and back in securely, and edit
household/profile settings. Every protected route is backed by a real database
session and household membership.

**Product assumptions for this milestone**

- v1 sharing stays `private` or household-wide. Per-member sharing is a later
  feature. M1 only creates the owner; member invitations are a later milestone,
  but the role model and membership table are built now.
- TOTP 2FA is **not** in M1. It is scheduled for M7, before self-hosting. Do not
  fake or stub a 2FA prompt. The setup security step explains the current
  protections and points to M7 for 2FA.
- The bank-sync country/provider is still an open decision. M1 stores an ISO
  country code on the household and uses it only for display/settings; M6 owns
  provider selection.
- The API moves to **port 8081** because 8080 is occupied by Docker's WSL relay.

## Out of scope

- Accounts, transactions, imports, budgets, goals, bank sync.
- Email delivery, invitations, password reset, email verification.
- TOTP, recovery codes, passkeys.
- Public signup, multi-household membership per user, per-member sharing.

## 1. Database

Create `apps/api/migrations/0001_identity.sql`. All timestamps are
`TIMESTAMPTZ NOT NULL DEFAULT now()`. Money is irrelevant in M1.

### `users`

| Column | Type | Notes |
|---|---|---|
| `id` | `UUID PRIMARY KEY DEFAULT gen_random_uuid()` | |
| `email` | `TEXT NOT NULL UNIQUE` | stored trimmed/lowercase; check `email = lower(email)` |
| `password_hash` | `TEXT NOT NULL` | Argon2id PHC string |
| `display_name` | `TEXT NOT NULL` | 1–80 chars |
| `locale` | `TEXT NOT NULL` | BCP-47, e.g. `en-US` |
| `timezone` | `TEXT NOT NULL` | IANA name, e.g. `America/New_York` |
| `currency` | `TEXT NOT NULL` | ISO-4217 display preference |
| `created_at`, `updated_at` | `TIMESTAMPTZ` | |

### `households`

| Column | Type | Notes |
|---|---|---|
| `id` | `UUID PRIMARY KEY DEFAULT gen_random_uuid()` | |
| `name` | `TEXT NOT NULL` | 1–80 chars |
| `base_currency` | `TEXT NOT NULL` | ISO-4217 |
| `country_code` | `TEXT` | ISO 3166-1 alpha-2, nullable until setup (setup sets it) |
| `created_at`, `updated_at` | `TIMESTAMPTZ` | |

### `household_members`

- `household_id UUID NOT NULL REFERENCES households(id) ON DELETE CASCADE`
- `user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE`
- `role TEXT NOT NULL CHECK (role IN ('owner', 'admin', 'member'))`
- `joined_at TIMESTAMPTZ NOT NULL DEFAULT now()`
- Primary key `(household_id, user_id)`.
- Index `(user_id)` for session/auth lookups.

### `sessions`

- `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`
- `user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE`
- `token_hash BYTEA NOT NULL UNIQUE` — SHA-256 of the opaque token
- `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`
- `last_seen_at TIMESTAMPTZ NOT NULL DEFAULT now()`
- `expires_at TIMESTAMPTZ NOT NULL`
- `ip TEXT`, `user_agent TEXT`
- Index `(user_id)` and `(expires_at)`.

### `audit_log`

- `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`
- `user_id UUID REFERENCES users(id) ON DELETE SET NULL`
- `household_id UUID REFERENCES households(id) ON DELETE SET NULL`
- `action TEXT NOT NULL`
- `entity TEXT`, `entity_id UUID`
- `metadata JSONB NOT NULL DEFAULT '{}'::jsonb`
- `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`
- Index `(household_id, created_at DESC)` and `(user_id, created_at DESC)`.

Add a trigger or application-level update for `updated_at` only if it stays
simple; application-managed `updated_at` is acceptable.

## 2. Backend requirements

### Configuration

Add to `Config` and `.env.example`:

- `APP_ORIGIN` — default `http://localhost:5173`; exact origin expected for
  mutating browser requests.
- `COOKIE_SECURE` — default `false`; must be `true` behind production HTTPS.
- Existing `DATABASE_URL`, `HOST`, `PORT` stay. Keep port 8081.

Run `sqlx::migrate!("./migrations")` at startup after connecting to Postgres.
Use a real connection (`PgPoolOptions::connect`) and fail fast with a clear error
if the database is unavailable. Keep `/api/health` and `/api/ready` working.

### Dependencies

Add only what is needed. Suggested: `argon2`, `rand`, `sha2`, `base64`,
`axum-extra` with `cookie`, `uuid` with `v4`/`serde`, `chrono` with `serde`,
`thiserror`, `tower-governor`, `tower-http` with `request-id`, `set-header`, and
`timeout` if used. Add `migrate`, `macros`, `chrono`, `uuid` to `sqlx` features.
Use SQLx runtime queries while the schema is new; parameterized queries only.

### Modules

Keep the existing `config` and `health`; add a clean module layout, for example:

```
src/
  auth/          password.rs, session.rs, extractor.rs, routes.rs, csrf.rs
  households/    routes.rs, repository.rs
  audit.rs
  error.rs
  validation.rs
```

### Password handling

- Argon2id with a per-user random salt and current recommended parameters.
- Verify with constant-time password-hash verification from the `argon2` crate.
- Setup password policy: 12–128 characters, must not equal the email or display
  name, and must pass a strength check (`zxcvbn` score >= 3 is acceptable).
- Login failures always return the same generic error and status. Do not reveal
  whether the email exists.
- Do not log passwords or password hashes.

### Sessions and cookies

- Opaque token: at least 32 random bytes, URL-safe encoded. Store only SHA-256
  hash in `sessions.token_hash`.
- Session cookie: `expenser_session`, `HttpOnly`, `SameSite=Lax`, `Path=/`,
  `Secure` from `COOKIE_SECURE`, `Max-Age` matching absolute expiry.
- CSRF cookie: `expenser_csrf`, not HttpOnly, same `SameSite`/`Path`/`Secure`
  settings. Generate a random value per session response.
- Absolute session expiry: 30 days. Idle expiry: 14 days since `last_seen_at`.
  Update `last_seen_at` at most once per hour.
- Login always creates a new session; delete expired sessions for the user
  opportunistically. Logout revokes the current session. "Sign out everywhere"
  revokes every session for the user.
- On `/api/auth/me`, if the session is valid but the CSRF cookie is missing, set
  a fresh CSRF cookie in the response.

### CSRF and Origin

- For every `POST`, `PATCH`, `PUT`, and `DELETE` under `/api`, require an
  `Origin` header exactly equal to `APP_ORIGIN`. Reject missing/mismatched
  origins with `403` and a JSON error. This includes setup and login.
- For authenticated mutating routes, also require `X-CSRF-Token` equal to the
  `expenser_csrf` cookie. Use a constant-time comparison. Reject with `403`.
- GET/HEAD requests are exempt from CSRF but still require authentication where
  noted.
- Tests must set `Origin`; this is intentionally strict.

### Rate limiting

Use `tower-governor` if it is compatible with the current Axum/Tower versions. If
it is not, implement a small, documented in-memory per-IP limiter that is
periodically cleaned. Requirements:

- Login: 10 attempts per 5 minutes per IP, including failed logins. Return `429`
  with a generic JSON error and `Retry-After` if practical.
- Setup: 5 attempts per 15 minutes per IP.
- Do not rate-limit `/api/health` or `/api/ready` in a way that breaks probes.
- Use the peer socket address in M1. Reverse-proxy client-IP handling is an M7
  deployment concern; document it.

### Security headers / errors

Add `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`,
`X-Frame-Options: DENY`, and `Cache-Control: no-store` on auth responses.
Structured JSON errors:

```json
{ "error": { "code": "invalid_credentials", "message": "Email or password is incorrect." } }
```

Never return SQLx/database errors, hashes, tokens, or stack traces to clients.

### Audit logging

Write audit rows for: `setup_completed`, `login_succeeded`, `login_failed`,
`logout`, `logout_all`, `profile_updated`, `household_updated`. Include useful
metadata (IP, user agent, changed field names) but never passwords/tokens.

## 3. API contract

All request/response fields are camelCase. All routes are under `/api`.

### Public

`GET /api/setup/status`
→ `200 { "needsSetup": true }`

`POST /api/setup`
```json
{
  "displayName": "Avery Stone",
  "email": "avery@example.com",
  "password": "correct horse battery staple",
  "householdName": "Stone Household",
  "countryCode": "US",
  "baseCurrency": "USD",
  "locale": "en-US",
  "timezone": "America/New_York"
}
```
→ `201` auth payload + session cookies. Only works while `users` is empty.
Use a transaction and a PostgreSQL advisory lock so two concurrent setup
requests cannot both succeed. Second attempt → `409 setup_already_complete`.

`POST /api/auth/login`
```json
{ "email": "avery@example.com", "password": "..." }
```
→ `200` auth payload + new session cookies. Invalid credentials → `401`
`invalid_credentials` (generic). Rate limited.

### Authenticated

`GET /api/auth/me` → `200` auth payload, or `401 unauthenticated`.

Auth payload:
```json
{
  "user": {
    "id": "uuid",
    "email": "avery@example.com",
    "displayName": "Avery Stone",
    "locale": "en-US",
    "timezone": "America/New_York",
    "currency": "USD"
  },
  "household": {
    "id": "uuid",
    "name": "Stone Household",
    "baseCurrency": "USD",
    "countryCode": "US"
  },
  "role": "owner"
}
```

`POST /api/auth/logout` → `204`, clears both cookies, revokes current session.
Requires Origin + CSRF.

`POST /api/auth/logout-all` → `204`, revokes all sessions for the user, clears
cookies. Requires Origin + CSRF.

`GET /api/household/members` → `{ "members": [ { "id", "displayName",
"email", "role", "joinedAt" } ] }`. Only include email for the owner/admin
viewer or for the viewer's own row.

`PATCH /api/me` — any authenticated member. Optional fields: `displayName`,
`locale`, `timezone`, `currency`. Validate lengths and formats. Returns updated
auth payload.

`PATCH /api/household` — owner/admin only. Optional fields: `name`,
`baseCurrency`, `countryCode`. Returns updated auth payload. Members get `403`.

Keep `/api/health` and `/api/ready` unchanged.

## 4. Frontend requirements

### Palette

Apply the tokens in `docs/design/PALETTE.md` via Tailwind v4 `@theme` in
`apps/web/src/index.css`. Replace raw slate/emerald styling in the shell and
pages with semantic tokens (`bg-canvas`, `bg-surface`, `border-line`,
`text-ivory`, `text-sage`, `text-growth`, `text-wealth`, `text-danger`, etc.).
Add a system-serif display font token for auth/setup headings. Keep the 8081
Vite proxy.

### Auth client

- Add typed API helpers with `credentials: 'same-origin'`.
- Add a small CSRF helper that reads the `expenser_csrf` cookie and sends
  `X-CSRF-Token` on POST/PATCH/PUT/DELETE.
- Add an auth query for `/api/auth/me` and a setup-status query.
- Router guards:
  - If `needsSetup` is true, the app routes redirect to `/setup`.
  - `/setup` redirects to `/login` once setup is complete.
  - `/login` redirects to `/` when already authenticated.
  - Protected routes redirect to `/login` on 401.
  - No flash of protected content while auth is loading; show a branded splash.
- Use TanStack Router `beforeLoad`/`redirect` with router context containing the
  QueryClient, or an equivalent guard that meets the same behavior.

### Setup wizard

Route `/setup`, polished and responsive. Steps:

1. **Owner account** — display name, email, password, confirm password. Show
   password guidance (12+ chars, strength), not a fake strength meter with
   random scores. Client validation + server errors.
2. **Household** — household name, country select (broad ISO list is fine),
   privacy explanation: accounts default private; sharing is explicit; admins
   have no override.
3. **Money & locale** — base currency, locale, timezone. Suggest sensible
   defaults from country but keep all fields editable. Use `Intl` APIs to list
   currencies/timezones where practical; if the list is static, keep it broad
   and documented. Preview a formatted date and currency amount.
4. **Review & security** — summary, note that 2FA arrives in M7, create button.
   On success, navigate to `/` and load the dashboard.

Show field-level errors and a form-level error without leaking server internals.
Avoid fake progress. Back/Continue controls must be keyboard accessible.

### Login

Route `/login`, same visual language. Email/password, generic error for bad
credentials, rate-limit message, disabled/loading state. No "forgot password"
link that does nothing; a short note that recovery is coming later is acceptable.
If setup is incomplete, direct users to `/setup`.

### Authenticated shell

- Replace the placeholder "S" with the user's initials/display name and show the
  household name in the desktop header.
- Add a logout action (dropdown or button) that calls the API and returns to
  `/login`.
- Keep the existing nav; settings becomes a real page.
- Dashboard: greet the user, show household name, keep the service-health card,
  and keep financial placeholders honest. No fake balances.
- Setup/login must not use the app shell.

### Settings

Route `/settings`, real forms:

- **Profile:** display name, email (read-only), locale, timezone, display
  currency. Save via `PATCH /api/me`; show success/error.
- **Household:** name, base currency, country. Editable for owner/admin; disabled
  for members. Save via `PATCH /api/household`.
- **Members:** list from `/api/household/members` with role badges.
- **Security:** "Sign out" and "Sign out everywhere" with confirmation. Note
  that TOTP/recovery codes arrive in M7.
- Use accessible labels, disabled/loading states, and no optimistic success that
  hides server failure.

## 5. Tests and verification

### API tests

Add integration tests using `#[sqlx::test(migrator = "crate::MIGRATOR")]` or the
equivalent, so each test gets a migrated temporary database. Cover at least:

1. `/api/setup/status` is true on an empty database.
2. Setup succeeds, returns 201, sets cookies, and creates user + household +
   owner membership + audit row.
3. A second setup attempt returns 409 and does not create another user.
4. Login succeeds with the correct password and fails generically with a wrong
   password.
5. `/api/auth/me` works with a session cookie and returns 401 without one.
6. Logout revokes the session and clears cookies.
7. A mutating authenticated request without `X-CSRF-Token` returns 403.
8. A mutating request with the wrong `Origin` returns 403.
9. Duplicate email/normalization behaves correctly.
10. `PATCH /api/household` rejects a member and accepts owner/admin.
11. Password hashing tests: hash != password, verify true/false.

Use a test helper that captures `Set-Cookie` headers and sends them back. Keep
tests deterministic; no sleeps except where an expiry test is explicit.

### Manual/UI checks

- Fresh database → `/setup`; complete wizard; land on dashboard.
- Refresh → still signed in; no flash of login.
- Sign out → `/login`; sign in again.
- Settings save → persists after refresh.
- "Sign out everywhere" → current session invalid.
- Wrong origin/CSRF rejected via API probes.
- Rate limit returns 429 after the threshold.
- Mobile layout at ~390px and desktop at ~1440px.

### Standard checks

```powershell
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
pnpm --filter @expenser/web lint
pnpm --filter @expenser/web build
```

## 6. Acceptance criteria

- [ ] Fresh database starts in setup mode and cannot be set up twice concurrently.
- [ ] Setup creates an Argon2id-protected owner, household, owner membership, and
      session; the owner is signed in immediately.
- [ ] Login, logout, logout-all, `/auth/me` work and use opaque, hashed,
      server-side sessions.
- [ ] Session cookie is HttpOnly/SameSite=Lax and Secure when configured; CSRF
      cookie + header are enforced on authenticated mutations.
- [ ] Origin check is enforced on all mutating API requests.
- [ ] Login/setup rate limits work.
- [ ] Generic auth errors; no secrets in responses or logs.
- [ ] Household role checks are enforced; no client-supplied household ID is
      trusted for a mutation.
- [ ] Settings persist and are household/profile scoped.
- [ ] Palette tokens are applied across setup, login, shell, dashboard, settings,
      and placeholders; no raw slate/emerald leftovers in app components.
- [ ] API integration tests cover the core auth/security flows and pass.
- [ ] Format, clippy, tests, web lint, and web build pass.
- [ ] README and PLAN reflect M1; screenshots are added by the main agent after
      the pipeline.
